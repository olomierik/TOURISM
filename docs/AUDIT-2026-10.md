# Explore Tanzania: audit and roadmap (2026-10-22)

This is the first step the build brief ("EXPLORE TANZANIA — Scalable travel marketplace and business acquisition
engine") asks for: inspect what exists, then plan in small phases. It also records why nobody could sign in or sign up,
and what this branch changes.

## 1. Why users could not sign up or sign in

**Root cause: production has no Supabase connection.** The live site (exploretanzania.online, now served by
**Netlify**) was built without `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Its JavaScript
holds `placeholder.supabase.co` and no real project URL.

Commit `44e7072` ("feat(auth,i18n): add demo user support", 2026-09-10) turned that from a crash into a silent fake.
Without the variables:

| What a visitor does | What happened |
|---|---|
| Signs up | "Check your inbox". No account is created and no mail is sent (a `demo_user` cookie only). |
| Signs in, any email, any password | "Succeeds" and lands on /account, filled from the cookie. Nothing is saved; the header still says "Sign in". |
| Email containing "admin" | Lands on /admin with the admin role. |
| Opens /admin with no cookie at all | The proxy let every protected request through, so the admin shell rendered. |
| Browses listings | Every query answered `[]`, so pages showed hardcoded "curated" businesses with invented 4.9★ ratings, "verified" badges, prices and WhatsApp numbers. |

Checked on 2026-10-22 in Chrome: a made-up address with a wrong password "signed in" and the /admin shell opened.

**The database itself is fine.** The Supabase project in the local `.env` answers: 2,626 businesses and 6 auth users.
Email sign-up is enabled; confirmation is required. The last real sign-in was 2026-09-23, around when production
lost its variables. The data is all there, but the live site can't reach it.

The move from Vercel to Netlify is the likely moment the variables were lost: the README and CI still say Vercel, and
the Netlify site isn't in the `godvilconsult-bit` Netlify team that Chrome is signed in to.

## 2. What this branch changes (`fix/auth-production-mode`)

| File | Change |
|---|---|
| `lib/auth/actions.ts` | Without Supabase, sign-in and sign-up refuse with "Sign-in is temporarily unavailable" (`unavailable`) instead of setting a cookie. An unreachable auth server is reported as `unavailable`, not "wrong password". In production, sign-up refuses when no email provider is configured, instead of "check your inbox" for a mail that is only logged. |
| `proxy.ts` | Protected routes (/admin, /dashboard, /account) fail closed: no Supabase, no user, or an error during the check all redirect to sign-in. |
| `app/[locale]/admin/layout.tsx` | A second lock: the layout checks the admin role itself and 404s otherwise. |
| `app/[locale]/account/page.tsx` | The `demo_user` cookie fallback is gone. |
| `scripts/check-env.mjs` + `prebuild` | A **production** build on Netlify (`CONTEXT=production`) or Vercel stops if the Supabase, site-URL or Resend variables are missing. The last good deploy stays live instead of being replaced by a silent fake. Local builds, CI and previews skip the check. |
| `lib/queries/curated-regional-businesses.ts` | The 27 sample listings keep their names but lose invented ratings, "verified" badges, featured tier, response rates, prices and WhatsApp numbers, and are flagged `isDemo` ("sample"). |
| `messages/{en,de,fr,it}.json` | The `unavailable` message. |
| `.env.example` | The documented version restored (the same commit had stripped every comment), plus the Google Maps keys. |

Old `demo_user` cookies are harmless now (nothing reads them) and are still cleared on sign-out.

## 3. Owner steps to bring sign-in back

1. **Netlify → the Explore Tanzania site → Site configuration → Environment variables.** Add, scoped to **Builds and
   Functions**, the values from your local `.env`:
   - `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` (mark secret)
   - `NEXT_PUBLIC_SITE_URL` = `https://www.exploretanzania.online` (or the apex, whichever is primary)
   - `RESEND_API_KEY` (secret), `EMAIL_FROM`, `OUTREACH_FROM`, `OUTREACH_REPLY_TO`
   - the AdSense, Search Console and indexing values you had on Vercel
   - Flutterwave keys only when payments are meant to be live
2. **Supabase → Authentication → URL configuration:** set Site URL to the live origin and add
   `https://www.exploretanzania.online/**` and `https://exploretanzania.online/**` to the redirect allow-list.
3. **Resend:** confirm `exploretanzania.online` is still verified (SPF/DKIM/DMARC), since sign-up mail goes through it.
4. Merge this branch, then **trigger a deploy**. `NEXT_PUBLIC_*` values are baked in at build time, so changing
   variables without rebuilding does nothing.
5. Check: sign up with a real address, receive the mail, confirm, sign in, open /account. Then open /admin signed out:
   it should redirect to sign-in.
6. Fix the README and CI comments that still say Vercel.

## 5. Gaps against the brief

| Area | Gap | Effort | Risk / dependency |
|---|---|---|---|
| **Auth (done here)** | Production silently disconnected | S | Owner sets Netlify env vars |
| Discovery engine | Discovery runs as scripts; no admin UI to pick country/region/radius/category, no job queue, progress, retries or per-source cost tracking | L | Google Places terms: store place IDs, refresh other fields, attribute; Kenya, Uganda and Rwanda licensing registers |
| Claim invitations | Exists, but tokens aren't single-use expiring claim links; no bounce/complaint webhooks from Resend | M | Resend webhooks; electronic-marketing rules per country (Tanzania's PDPA 2022, Kenya's DPA 2019, etc.) |
| Trial + plan | No 30-day trial, no reminder schedule; the brief's $200/yr conflicts with the $50/$75 the owner set in migration 044 | M | **Owner decision on price** |
| Entitlements | Plan features are spread through code, not one entitlements table | M | none |
| Marketplace payments | No connected-merchant checkout; Flutterwave is used for subscriptions only | L | A provider with split settlement in TZ/KE/UG/RW (Flutterwave subaccounts, Pesapal, DPO); legal review; no platform custody |
| Bookings | Enquiries only; no availability, booking state machine, cancellation or refunds | L | Depends on payments |
| Verified reviews | Reviews are open; nothing ties a review to a real booking | M | Depends on bookings |
| Swahili | **Done (Phase 2):** `sw` locale, 1,552 interface strings, Swahili URLs. Content (listings, guides) still reads English | M | Swahili content translations in the database |
| Sample data | Fallback listings render whenever a query fails, even in production | S | Done in part (no fake trust signals); next, show an error state instead |
| Observability | Errors only reach `console`; no alerting when auth or the database is unreachable | S | Sentry, or Netlify log drains |
| Docs | README and CI still describe Vercel | S | none |

## 6. Recommended order

1. **Phase 0 (done, PRs #47, #48):** restore auth, fail closed, block silent production builds; Railway hosting.
2. **Phase 1, trust and reliability (S–M):** remove the sample-data fallback from production paths (done, PR #49) (show "temporarily
   unavailable"), error monitoring, a health check that tests Supabase and Resend from the deployed site, README
   update.
3. **Phase 2, Swahili (M, done):** `sw` locale with localized slugs, so local businesses and Tanzanian travellers can use the
   site in their own language.
4. **Phase 3, claim funnel (M):** single-use expiring claim tokens, Resend delivery/bounce/complaint webhooks feeding
   suppression, daily send limits and campaign pause in the admin outreach page.
5. **Phase 4, trial and entitlements (M):** a 30-day premium trial on approved claims, an entitlements table, trial
   reminders (14/7/3/1 days), downgrade to free on expiry. Needs the price decision.
6. **Phase 5, admin discovery jobs (L):** a `discovery_jobs` table and queue (Supabase cron or a worker), Google Places
   (New) text and nearby search by region and radius, import preview, dedupe on name, domain, phone and distance,
   approval queue, per-source cost.
7. **Phase 6, marketplace payments and bookings (L):** provider capability registry, connected-merchant onboarding,
   booking and payment state machines, authenticated webhooks, reconciliation. Only after the provider and legal
   review; no real payments without the owner's approval.
